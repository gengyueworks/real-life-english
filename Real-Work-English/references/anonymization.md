# 匿名化与事实保护规则

## 目录

1. 基本原则
2. 信息映射
3. 数字处理
4. 事实保护
5. 发布前检查

## 一、基本原则

匿名化只改变能够识别个人、公司和项目的信息。必须保留业务逻辑，包括市场阶段、渠道模式、合作关系、权限边界、资源约束、利益冲突和条件交换。

原始资料留在用户项目中。不要复制到skill、公开仓库或示例目录。不要修改原始文件。

## 二、信息映射

| 原始信息 | 通用写法 |
| --- | --- |
| 用户姓名 | `Learner`或岗位名称 |
| 同事和客户姓名 | `Sales Director`、`Client Lead`等岗位 |
| 公司名称 | `HQ`、`Distributor`、`Retail Partner`、`Agency` |
| 产品名称 | `Product A`、`Product B`、`Hero Model` |
| 国家和城市 | `Market A`、`Market B`、`Market C` |
| 渠道和客户品牌 | `Key Retailer`、`Online Platform`、`Major Account` |
| 内部系统和项目名称 | `Project A`、`Internal System` |

岗位称呼需要保留真实决策关系。例如原角色是代理销售负责人，就不能改成普通营销执行人员。

## 三、数字处理

预算、价格、销量、库存、利润和时间数字可以采用以下方式：

1. 删除不影响训练逻辑的精确数字。
2. 改为区间，例如`a mid-five-figure budget`。
3. 按统一比例调整相关数字。
4. 使用合理的模拟数字，并标记`【模拟训练】`。

调整数字时保持：

- 原有量级关系
- 价格差比例
- 预算与项目规模的关系
- 库存、销量和时间窗口的约束
- 双方投入比例和谈判逻辑

不得单独修改一个数字，导致其他数据和业务判断失真。

## 四、事实保护

### 可以保留

- 已经确认的市场阶段
- 真实的渠道模式
- 双方职责和权限边界
- 已发生的执行问题
- 已确认的利益冲突
- 尚未解决的信息缺口

### 必须标记

- 推测的客户立场
- 根据岗位推测的场景
- 模拟的对话和异议
- 改写后的数字
- 尚待内部确认的商业条件

### 禁止

- 为了让故事完整虚构合作结果
- 将内部讨论写成客户承诺
- 将一个市场的事实移植到另一个市场后继续称为真实事实
- 用通用商业常识替代用户材料
- 脱敏后改变谁负责、谁决策或谁承担结果

## 五、发布前检查

使用搜索检查以下内容：

- 真实姓名
- 公司和品牌名称
- 产品型号
- 客户、渠道和agency名称
- 具体国家和城市
- 精确预算、销量、价格和库存
- 邮箱、电话、链接和内部系统名称

逐段检查：

1. 这一判断来自哪里？
2. 匿名化是否改变了业务阶段？
3. 角色权限是否仍然准确？
4. 冲突和利益关系是否仍然成立？
5. 模拟内容是否清楚标记？
